# Cloudflare 무료 운영 근거

확인일: 2026-11-03. 아래는 당일 공식 문서에서 확인한 한도입니다. 계정 플랜과 정책은 배포 전에 다시 확인합니다.

| 자원             | Workers Free 기준 | 설계 대응                                           |
| ---------------- | ----------------- | --------------------------------------------------- |
| Worker 요청      | 하루 100,000      | 매분 Cron 1,440회 + 소규모 사용자 API               |
| HTTP CPU         | 호출당 10ms       | 서버 렌더링 없이 정적 UI, Web Crypto, 작은 API 처리 |
| Cron CPU         | 호출당 10ms       | 한 번에 한 단계, 보고 페이지 25개                   |
| 외부 subrequests | 호출당 50         | 어댑터 공용 Http 예산 16회, 초과 시 영속 재시도     |
| 동시 외부 연결   | 6                 | 외부 API 순차 호출                                  |
| Cron 설정 수     | 계정당 5          | Cron 1개 사용                                       |
| 메모리           | isolate당 128MB   | DB·보고 무제한 메모리 적재 안 함                    |

CPU에는 외부 네트워크/D1 대기 시간이 포함되지 않습니다. Cron의 wall time이 길어도 Free CPU가 10ms라는 제약은 그대로입니다. [Workers 공식 한도](https://developers.cloudflare.com/workers/platform/limits/)

| --------------------- | -------------- | ----------------------------------- |
| 읽은 행               | 하루 5,000,000 | 키/인덱스 조회, 보고 정렬 인덱스    |

## 초기 규모 예산 — 실측이 아닌 가정

10명이 각각 하루 20번 API 요청하고, 새 이슈/수정 총 50건, 미완료 작업 100개, 매분 Cron을 가정합니다.

- HTTP 200회 + Webhook/명령 수십~수백 회 + Cron 1,440회: 통상 하루 수천 회 수준으로 100,000회보다 작습니다. 정적 asset 요청은 별도 정적 제공 경로입니다.
- 대기 중 Cron의 lease 삽입/삭제와 작업 조회가 하루 수천 행의 읽기/쓰기를 만듭니다. 로그인·보고·작업 처리 포함 **읽기 50,000행/일, 쓰기 20,000행/일 이하를 초기 관측 목표**로 둡니다. 지표가 아닌 계획치입니다.
- 10명 × 52주 × 응답 JSON 약 1KB면 순수 응답 데이터는 연간 0.52MB 수준입니다. 인덱스·row overhead·jobs·effects·보고 스냅샷을 포함하면 더 커집니다.
- 100개 보고 항목은 4번 Notion 조회, 100번 메시지 생성과 D1 상태 작업으로 나뉩니다. 분당 한 작업 단계이므로 게시 완료까지 약 105분 이상 걸릴 수 있습니다. 작은 팀의 실제 미완료 이슈 수를 확인하고 행 묶음 최적화가 필요하면 CPU 측정 후 도입합니다.
- 10명 미응답자는 23:00부터 큐에 배치되어 순차 DM을 받습니다. 정확한 동시 발송은 보장하지 않습니다.

**총량은 초기 규모에서 여유가 있을 것으로 추정하지만 무료 운영을 확정하지 않습니다.** 실제 배포의 Web Crypto, Intl 날짜 계산, JSON 정규화, D1 batch 오버헤드가 CPU 10ms 내인지 확인해야 합니다. 로컬 wall-clock 테스트나 번들 크기는 Cloudflare 과금 CPU의 측정값이 아닙니다.

## 실행 상한과 복구

외부 호출은 한 단계당 16회로 제한하고, Notion 보고는 25행 단위로 진행 상태를 저장합니다. 한 단계의 CPU가 초과되어 강제 종료되면 D1 lease 만료(3분) 후 이어갑니다. 생성 응답 유실은 무조건 POST를 반복하지 않고 요청 ID/게시물 표식으로 확인합니다.

동일 단계에서 CPU 초과가 반복되면 `enabled:false`로 예약 소비를 중단하고 페이지 크기·알림 처리량을 줄이세요. Free 요청/D1 한도가 소진되면 플랫폼이 거부할 수 있으며 앱이 자동 유료 전환하지 않습니다. 갱신 이후 실패 작업을 재등록하고 커서부터 복구합니다. 자세한 절차는 [복구 안내](recovery.md)에 있습니다.

## 운영 전 측정할 값

- 실제 Free 계정에 배포 후 이슈 생성·일정 개시·리마인더·보고·Webhook의 CPU p50/p95/p99, `exceededCpu`, subrequests를 확인합니다.
- D1 rows_read/rows_written/storage, Webhook 실패율과 429, 작업 큐 대기시간을 확인합니다.
- Notion의 API 속도 제한과 Discord의 Retry-After를 실제 응답으로 확인합니다. 현재 구현은 429 상태를 저장해 이후 실행으로 미룹니다. Notion 전체 DB를 상시 폴링하지 않습니다.
- 장기 보존 보고가 늘면 사전 export 후 보존 정책을 정합니다. 자동 삭제는 기본 제공하지 않습니다. 만료 세션·OAuth state·인증 코드 정리는 복구 문서의 SQL로 수행합니다.

배포가 안 된 현재는 위 운영 지표가 모두 **미측정**입니다. Free 플랜을 유료로 바꾸는 코드·CLI 단계·부가 서비스는 없습니다.
