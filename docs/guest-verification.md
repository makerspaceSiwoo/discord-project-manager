# 게스트 계정 연결: 반드시 실환경에서 확인할 사항

현재 실증 상태는 **미확인**입니다. 코드와 모의 API 테스트는 검증 방법을 구현한 것이며 실제 게스트 인증 성공을 의미하지 않습니다.

## 공용 권한과 개인 신원

공용 Internal Connection은 소유자가 이슈 DB와 인증 페이지에 부여하는 서버 권한입니다. 개인 연결은 Discord OAuth로 확인한 사용자 ID와 Notion 댓글의 `created_by.id`를 연결하는 절차입니다. 팀원은 개인 API 토큰을 제출하지 않습니다. 이름·이메일·People 드롭다운에서 임의 선택한 값은 신원 증거로 사용하지 않습니다.

[Notion 사용자 목록 API](https://developers.notion.com/reference/get-users)는 게스트를 반환하지 않습니다. 이미 알아낸 게스트 ID의 단일 사용자 조회는 별도 API이며, 그 응답도 대상 페이지의 현재 ACL을 증명하는 것은 아닙니다. [댓글 API](https://developers.notion.com/reference/list-comments)의 `created_by`를 사용하되 실제 권한으로 읽히는지 먼저 확인합니다.

## 1. OAuth 경로의 사전 실증

별도 검증용 Discord 서버와 Notion DB에서 다음을 기록합니다. 실제 사용자 토큰이나 전체 OAuth 응답을 저장소에 기록하지 않습니다.

| 확인 항목        | 통과 조건                                                                 | 현재 상태              |
| ---------------- | ------------------------------------------------------------------------- | ---------------------- |
| 계정 유형        | 두 사용자가 workspace member가 아닌 공유 페이지 guest임을 소유자가 확인   | 미확인                 |
| 게스트 OAuth     | 해당 workspace를 선택하고 OAuth 승인이 끝나는가                           | 미확인                 |
| 실제 사용자 ID   | OAuth 응답의 owner.user.id가 승인한 게스트임을 독립적으로 확인            | 미확인                 |
| 공용 연결과 구분 | OAuth로 선택한 페이지 권한을 공용 DB 접근 권한과 혼동하지 않음            | 설계 반영, 실증 미확인 |
| People 지정      | 공용 연결로 얻은 ID를 대상 DB 전용 테스트 행에 지정하고 재조회 시 동일 ID | 미확인                 |

게스트가 workspace를 선택할 수 없거나 응답에서 실제 사용자 ID를 확인할 수 없으면 OAuth 경로는 채택하지 않습니다. 현재 구현에는 **개인 Notion OAuth 연결 경로를 넣지 않았습니다**. Discord OAuth만 동작하며, 아래 댓글 연결에서 사용자마다 실제 검증을 수행합니다. OAuth를 추가할 때도 프로젝트·Discord 세션에 바인딩된 state, workspace ID 검증, 동일 ID 유일성, People 지정 검증은 그대로 적용해야 합니다. [공식 OAuth 흐름](https://developers.notion.com/guides/authorization/overview)

## 2. 댓글 대안의 격리된 검증

실제 업무 행은 검증 대상으로 사용하지 않습니다. 인증 페이지와 전용 `probePageId`를 준비하고 `linkingEnabled: true`로 본인 확인 절차를 엽니다. 투표·보고 알림은 `features.automation: false`로 유지한 상태에서 먼저 시험합니다. 게스트 실증 전에는 `guestVerificationEnabled: false`와 빈 `guestEvidence`를 유지하며 검증 기록을 임의로 만들지 않습니다.

1. 소유자가 인증 페이지를 게스트에게 댓글 가능 권한으로 공유하고 공용 연결의 댓글 읽기 capability를 켭니다.
2. 게스트 A가 Discord로 로그인한 원래 브라우저에서 코드를 발급합니다. 코드는 192비트 난수, 10분 만료이며 D1에는 해시만 저장합니다. 발급은 사용자당 1분 간격이고 새 발급은 이전 코드를 폐기합니다.
3. 게스트 A가 지정 페이지에 **수정하지 않은 새 댓글**로 코드를 작성합니다. 실제 댓글 작성자가 A의 Notion 계정인지 확인합니다.
4. 원래 Discord 세션에서 댓글 확인을 누릅니다. 서버는 100개씩 최대 5페이지를 읽습니다. 일치 댓글이 정확히 하나이고 발급 이후·만료 이전에 작성되었으며 수정되지 않았어야 합니다.
5. 화면의 실제 사용자 이름·이메일(권한이 없으면 미제공)과 **Notion ID**를 본인 계정과 대조합니다. 원래 Discord 사용자가 명시적으로 확인해야 하며 서버가 첫 댓글을 자동 선점 연결하지 않습니다.
6. 최종 확인 시 댓글을 다시 조회하고 후보 ID와 댓글 ID가 유지되는지 확인합니다. 프로젝트별 잠금 아래 전용 probe 행이 대상 data source에 있는지 확인한 뒤 People을 지정하고 재조회합니다. 지정된 ID가 정확히 일치할 때만 연결을 저장합니다.
7. DB의 `(project_id, discord_id)`와 `(project_id, notion_id)` 유일성, 코드 소비를 하나의 D1 batch로 처리합니다. 충돌이나 만료면 연결하지 않습니다.
8. 실제 이슈 생성에서 해당 ID가 담당자로 지정되는지 확인합니다.

## 3. 공격·오류 사례

| 시나리오                                       | 기대 동작                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 다른 Discord 사용자가 코드를 복사              | 원래 세션에 바인딩되어 inspect/confirm 거부                                                       |
| 게스트 B가 A의 댓글 코드를 복사해 추가 댓글    | 중복 댓글이면 연결 거부, 새 코드로 다시 시작                                                      |
| B 댓글이 먼저 보임                             | 자동 연결 안 함. 원래 Discord 사용자가 이름/ID를 확인하고 본인이 아니면 취소. 최종 확인 시 재조회 |
| 댓글을 수정하여 코드 추가                      | 거부. 새 댓글로 재시도                                                                            |
| 코드 만료 또는 재사용                          | 거부                                                                                              |
| 서로 다른 Discord 계정이 같은 Notion 계정 연결 | 유일 제약으로 충돌. 관리자 임의 매칭 대신 원래 연결 해제                                          |
| 인증 페이지 댓글을 API가 못 읽음               | 연결하지 않음. 권한 수정 후 새 코드                                                               |
| 500개 이상의 댓글 때문에 전체 확인 불가        | 연결하지 않음. 인증 페이지 교체/정리 후 새 코드                                                   |
| 봇/연결의 댓글                                 | 사용자 조회 type이 person이 아니면 거부                                                           |
| People 지정 거부·다른 ID 반환·응답 유실        | 연결하지 않음. 재시도                                                                             |
| probe 검증 동시 실행                           | 프로젝트별 lease로 직렬화                                                                         |
| 원래 브라우저 세션 만료/로그아웃               | 새 로그인과 새 코드 필요                                                                          |

공개 댓글의 코드는 보이는 값입니다. 복사를 원천 차단하거나 Notion 계정 주인이 아닌 사람이 댓글을 작성할 수 있는 권한 오남용까지 막는 비밀 증거로 취급하지 않습니다. 본인 확인 UI, 정확히 하나의 수정되지 않은 댓글, 재조회와 원래 세션 확인이 모두 필요합니다. 작업 공간 관리자나 페이지 편집자가 신뢰할 수 없는 운영 환경에는 이 방식을 활성화하지 마세요. 댓글 API만으로 동시 시점의 완전한 원자적 스냅샷은 보장할 수 없습니다.

## 4. 접근 철회와 재연결

- Discord 탈퇴/역할 상실은 다음 API 요청 시 연결·세션을 삭제합니다. 예약 DM과 담당자 알림에서도 현재 역할을 확인합니다.
- 개인은 계정 연결 화면에서 해제할 수 있으며 진행 중인 코드도 무효화됩니다. 재연결은 새 코드로 동일 검증을 다시 수행합니다.
- Notion의 개별 페이지 접근 철회는 API가 즉시 알려준다고 가정하지 않습니다. 운영자는 `/api/admin/revoke`로 연결과 세션을 철회합니다. 기본 `linkLifetimeDays: 0`은 검증된 연결을 기한 없이 저장합니다. 본인의 연결 해제, 관리자 철회, 확인된 Discord 탈퇴/필수 역할 상실 시 연결을 삭제합니다. 정기 재검증이 필요한 팀은 1~30일을 설정할 수 있습니다. 최초 인증 코드는 계속 10분 뒤 만료되며, 웹 로그인 세션 만료와 계정 연결 유지는 별개입니다.
- 계정 철회 후 이미 생성된 Notion 작업의 담당자를 자동 삭제하지 않습니다. 기준 데이터인 Notion에서 운영자가 명시적으로 변경합니다.
- 댓글 권한만 있고 이슈 DB 접근이 없는 사람도 People 속성에 들어갈 수 있는지 반드시 시험합니다. **People 지정 성공은 그 사람이 이슈를 읽을 수 있다는 증명이 아닙니다.** 대상 DB의 실제 공유 권한을 별도로 확인하고 증거에 적습니다.

## 검증 증거 양식

비밀값 없이 검증 일시, API 버전, 시험 workspace/data source, guest임을 확인한 방법, OAuth 성공/실패 이유, 댓글 조회·created_by 확인, People 지정·읽기 결과, 실제 이슈 열람 여부, 위 공격 테스트 결과를 기록합니다. 운영 `guestEvidence`에는 이 기록 위치와 검증 일시를 적습니다. 현재 저장소에는 실제 성공 증거가 없습니다.
